# A Transformer chatbot from scratch in PyTorch

This is an educational, decoder-only Transformer that generates replies one
UTF-8 byte at a time. It starts with random weights: no pretrained model,
external AI API, or model download. Only PyTorch is required.

The included synthetic conversations demonstrate the complete pipeline. They
are far too small to teach general language understanding. Expect overfitting,
repetition, and poor or nonsensical replies, especially to unfamiliar prompts.
Low training loss is not evidence of useful conversation ability.

## Quick start on Linux

Use Python 3.10 or newer with a supported PyTorch build. Extract the archive,
open a terminal inside `transformer_chatbot`, and run:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install 'torch>=2.6,<3' --index-url https://download.pytorch.org/whl/cpu
python -m unittest -v
python train.py --epochs 200
python chat.py --checkpoint checkpoints/best.pt
```

For CUDA, use the appropriate installation command from
https://pytorch.org/get-started/locally/ instead. Training detects CUDA, then
Apple MPS, then CPU. Chat defaults to CPU; add `--device cuda` or `--device mps`
if your installation supports it. Training time depends on your hardware.

Two inference checkpoints are saved: `best.pt` has the lowest validation loss,
and `last.pt` has the final epoch's weights. These files contain the architecture
configuration and weights. They do not include optimizer state for resuming
training; rerunning `train.py` starts a fresh model.

In chat, `/reset` clears history and `/quit` exits. Try greetings or topics from
the demo data, but do not expect the model to reliably reproduce its examples.

## What is more advanced than the intent chatbot?

| Feature | Intent classifier | This project |
| --- | --- | --- |
| Output | Selects a handwritten reply | Generates the next token repeatedly |
| Text representation | Bag of words | Ordered byte tokens with positions |
| Model | Feedforward classifier | Transformer with explicit causal attention |
| Conversation | Each message independent | Recent turns included in the prompt |
| Training | One intent label per message | Next-token labels for assistant replies |
| Evaluation | Training loss only | Separate conversation validation split |
| Reuse | Retrains at startup | Saves and loads model checkpoints |

## Files and suggested reading order

1. `data.py`: tokenizer, roles, next-token target alignment, and split.
2. `model.py`: attention, Transformer blocks, and vocabulary prediction.
3. `train.py`: batching, supervised loss, optimization, and validation.
4. `chat.py`: sampling and conversation history.
5. `test_chatbot.py`: checks for data alignment, causal attention, padding,
   loss reduction, checkpoint loading, and bounded generation.

## How a conversation becomes training data

For a conversation with one user turn and one assistant turn, the token stream is:

```
BOS USER user_bytes EOS ASSISTANT assistant_bytes EOS
```

The model input is the stream without its last token. Targets are the same
stream shifted one position left. At each input position, the model predicts
the next token. User content, role markers, and padding have target `-100`, so
they do not contribute to the loss. Assistant bytes and the assistant's EOS do
contribute. The assistant role marker's position predicts the first reply byte.

Teacher forcing supplies the correct previous assistant bytes during training.
During inference, the model receives its own previously generated bytes. This
difference is one reason generation may fail even when training loss is low.

The tokenizer maps UTF-8 byte values 0..255 to token IDs 5..260, with five reserved
IDs for padding, beginning, ending, and the two roles. There are no unknown
tokens, and user-written marker strings cannot become reserved role tokens.
Byte tokenization costs more tokens than typical subword tokenization. A poorly
trained model can generate invalid UTF-8; decoding replaces invalid sequences
with the replacement character.

## How the Transformer works

Token embeddings give each token a learned numeric representation. Position
embeddings encode its order. Each Transformer block uses pre-layer normalization,
multi-head attention, residual connections, and a feedforward network with GELU.
Dropout regularizes training. A final linear layer produces 261 raw scores,
one for every possible next token.

In one attention head:

```
scores = Q @ K.T / sqrt(head_width)
scores[future_positions] = -infinity
weights = softmax(scores)
output = weights @ V
```

The causal mask prevents each position from seeing later tokens, including later
reply bytes. Otherwise training would let the model see the answer it must
predict. Batches use right padding; padding labels are ignored and future padding
is hidden from real tokens by the causal mask.

Default settings are two blocks, three heads, embedding width 96, and a context
window of 256 byte/special tokens. The implementation recomputes attention during
each generation step; it does not implement a key/value cache.

## The training loop

```python
logits = model(x)
loss = cross_entropy(logits, shifted_assistant_targets, ignore_index=-100)
optimizer.zero_grad()
loss.backward()
clip_grad_norm_(model.parameters(), 1.0)
optimizer.step()
```

The actual loop computes token-weighted loss, uses AdamW, and validates after
every epoch with dropout disabled and gradients off. Conversations, rather than
individual turns, are split into training and validation sets. Exact duplicate
conversations are rejected before the split. If your real dataset has related
conversations from the same person or session, group those together when preparing
separate datasets to avoid misleading validation results.

Validation is a language-model loss on held-out replies, not a test of factual
accuracy or conversational usefulness. The toy validation set is especially noisy.

## Use your own data

Write one JSON object per line, with alternating user/assistant messages:

```json
{"messages":[{"role":"user","content":"What is a Python list?"},{"role":"assistant","content":"A list is an ordered, mutable collection."}]}
{"messages":[{"role":"user","content":"My name is Kyler."},{"role":"assistant","content":"Hello, Kyler!"},{"role":"user","content":"What is my name?"},{"role":"assistant","content":"Your name is Kyler."}]}
```

Save it as `my_data.jsonl` and run:

```bash
python train.py --data my_data.jsonl --out my_checkpoints --epochs 100
python chat.py --checkpoint my_checkpoints/best.pt
```

All conversations must end with an assistant turn. Every conversation must fit
the selected context window; long records produce a useful error instead of
silently discarding training targets. For larger examples, use `--block-size 512`
or more. Attention memory grows quadratically with sequence length.

Use many diverse, high-quality examples for a narrow topic. This tiny architecture
and demo dataset are a learning project, not a route to general ChatGPT-level
ability. Training broad language ability from random weights requires much more
data and computation than this example provides.

## Generation controls

```bash
python chat.py --temperature 0.7 --top-k 40 --top-p 0.9 --max-tokens 160
python chat.py --temperature 0
```

- Temperature below 1 sharpens the distribution. Zero selects the highest score
  deterministically; it does not guarantee correctness.
- Top-k restricts candidates to the highest-scoring k tokens; 0 disables it.
- Top-p keeps a set whose cumulative probability reaches the chosen threshold.
- EOS ends a reply. The token limit also prevents unbounded generation.

History contains up to four previous turns by default. At each generation step,
only the latest `block_size` tokens are sent to the model; older text may be lost,
and truncation can cut through a turn. This is prompt context, not persistent
memory. Multi-turn behavior must also be represented in training data.

## Extensions worth implementing next

- Larger training data and a more efficient subword tokenizer.
- A separate language-model pretraining stage before conversation training.
- Grouped dataset splits and human evaluation on unseen questions.
- Optimizer-state checkpoints, learning-rate scheduling, and mixed precision.
- Key/value caching and conversation truncation at turn boundaries.
